# آرشیو کامل تاریخچهٔ سفارش در حالت آفلاین — ۲۰۲۶-۱۰-۲۶

## رفتار

- endpoint دستگاه جفت‌شده GET /api/offline-dashboard/order-history با مجوز cashier_pos سفارش‌های حذف‌نشدهٔ همان کسب‌وکار را در صفحه‌های ۵۰تایی می‌خواند. ترتیب keyset بر createdAt DESC, id DESC است و cursor زمان را با دقت میکروثانیهٔ PostgreSQL نگه می‌دارد؛ تبدیل به زمان میلی‌ثانیه‌ای مرورگر/Node دیگر نمی‌تواند ردیف را بین صفحات جا بیندازد. tenant از query یا payload کاربر پذیرفته نمی‌شود. API همان حفاظت Bearer terminal، فعال‌بودن صادرکننده/کسب‌وکار و rate limit دستگاه در offlineAuth را دارد.
- payload هر سفارش شامل خطوط/گزینه‌ها، جمع و وضعیت سفارش/پرداخت، جزئیات ضروری مشتری/تحویل و بخش امن تفکیک تسویه است. فیلدهای غیرضروری credential و idempotency ارسال نمی‌شوند؛ اندازهٔ صفحه ۴MB محدود است.
- worker پس از snapshot سریع آخرین ۱۰۰ سفارش، حداکثر ۲۰ صفحهٔ ۵۰تایی را در هر batch دریافت می‌کند. تا وقتی آرشیو کامل نشده batch بعدی هر ۶۰ ثانیه تلاش می‌شود؛ پس از تکمیل، بازبینی دوره‌ای هر ۱۰ دقیقه است. cursor سرور در setting رمز‌شدهٔ محلی نگه‌داری می‌شود؛ پس از restart یا قطع اتصال، صفحهٔ بعدی ادامه می‌یابد. سفارش‌ها با کلید کسب‌وکار/شناسه upsert می‌شوند تا همپوشانی با snapshot آخرین ۱۰۰ سفارش تکراری نسازد.
- جدول SQLite با نام offline_order_history جزئیات هر سفارش را با DPAPI رمز می‌کند و index زمان/شناسه برای پیمایش دارد. تب «تاریخچه سفارش‌های رستوران» صفحه‌های محلی ۱۰۰تایی را نشان می‌دهد و همان مودال جزئیات صندوق را برای هر سفارش باز می‌کند. آرشیو تا زمانی که مجوز دستگاه لغو نشده روی همان دستگاه می‌ماند؛ پاسخ 401/403 هم snapshot و هم آرشیو را پاک می‌کند.
- فروش‌های ثبت‌شده روی همین دستگاه همچنان در جدول جداگانهٔ محلی صفحه‌بندی می‌شوند و برای تاریخچه به اتصال یا کامل‌شدن آرشیو سرور وابسته نیستند.

## محدودیت و اعتبارسنجی

- کاربر در قطعی اینترنت فقط سفارش‌هایی را می‌بیند که پیش از قطعی روی دستگاه cache شده‌اند؛ برای سابقهٔ کامل باید دستگاه هنگام اتصال آنلاین بماند تا وضعیت آرشیو «کامل» شود. UI تعداد محلی و وضعیت «در حال تکمیل» را نشان می‌دهد. سفارش‌های جدید از snapshot آخرین ۱۰۰ سفارش وارد آرشیو می‌شوند. صفحه‌های تاریخی جزئیات را در لحظهٔ دریافت ذخیره می‌کنند؛ این فهرست فقط‌خواندنی است و تغییرات وضعیت سفارش‌های قدیمی را آفلاین اعمال نمی‌کند.
- حجم ذخیرهٔ آرشیو با سابقهٔ کسب‌وکار رشد می‌کند و در این مرحله retention/پاک‌سازی دستی ندارد.
- اعتبارسنجی این نوبت: `npm run typecheck`، ESLint هدفمند برای APIهای آفلاین، `node --check windows-bridge/ui/pos.js` و `git diff --check` موفق شدند. به درخواست کاربر، دیتابیس، تست integration و migration اجرایی نشدند. `cargo` و `rustc` در محیط نصب نیستند؛ کامپایل Tauri و اجرای واقعی روی Windows تأیید نشده است.
