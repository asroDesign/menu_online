# نمایشگر آشپزخانه

> مشخصات بازسازی عامل برای صفحه/جریان عمومی یا سیستمی.

- مسیر: `/tablet/:code`
- منبع فعلی: `src/app/tablet/[code]/page.tsx + src/components/kitchen-display.tsx`
- هدف: نمایش سفارش‌های ورودی برای kitchen tablet بدون login تعاملی.

## رابط و جریان

صفحه تمام‌صفحه با ستون سفارش تازه/در حال آماده‌سازی/آماده؛ شماره و میز/نوع، زمان و خطوط سفارش/تغییرات/یادداشت؛ دکمه‌های تغییر status؛ refresh خودکار/صدا در صورت فعال.

## API و داده

device code endpoint GET/POST `/api/device/:code/orders`; page code را اعتبارسنجی می‌کند.

## قواعد بازسازی

device code scoped/revocable؛ انتقال فقط statusهای مجاز؛ در reconnect duplicate action idempotent؛ عرض ثابت کارت و خوانایی از دور.

برای schema دقیق و شرط‌های موجود، فایل‌های source و API بالا را بخوان. UI عمومی باید tenant-isolated، RTL و responsive باشد.

## مشخصات سطح پیاده‌سازی

### قرارداد دستگاه و polling

`/tablet/:code` یک device code را اعتبارسنجی می‌کند؛ کد معادل دستگاه مجاز است و نباید در UI یا logهای قابل مشاهده افشا شود. `GET /api/device/:code/orders` سفارش‌های همان دستگاه/کسب‌وکار و دسته‌های مجاز را می‌دهد؛ `POST` همان endpoint برای تغییر وضعیت استفاده می‌شود. نمایشگر هر ۵ ثانیه وضعیت تازه می‌گیرد و هنگام unmount timer را پاک می‌کند.

### بورد سفارش

کارت سفارش باید شماره، نوع/نام میز، زمان ایجاد، اقلام با تعداد و انتخاب‌ها/یادداشت، نام مشتری در صورت لزوم و گام جاری را نشان دهد. ستون‌ها/فیلترها سفارش‌های تازه، در آماده‌سازی و آماده را جدا می‌کنند. انتقال اصلی `pending → preparing → ready → served` است؛ اقدام بعدی متناسب با وضعیت ارائه شود. UI ابتدا به‌روزرسانی خوش‌بینانه می‌کند و در خطا state قبلی را بازمی‌گرداند و پیام واضح می‌دهد.

### معیار پذیرش

پاسخ API باید فقط قلم‌هایی را بدهد که دستگاه دسته‌بندی مجاز آن را می‌بیند؛ اطلاعات سفارش در tenant جدا نشت نکند. قطع اتصال با نشان stale و refresh خودکار بازیابی شود؛ action تکراری/دو کلیک نباید سفارش را از وضعیت نامعتبر عبور دهد. خوانایی از فاصله، فونت و دکمه بزرگ، صدای اطلاع‌رسانی فقط طبق setting و کارکرد صفحه در نمایشگر touch بررسی شوند.
