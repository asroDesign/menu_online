# نتیجه پرداخت

> مشخصات بازسازی عامل برای صفحه/جریان عمومی یا سیستمی.

- مسیر: `/pay/result`
- منبع فعلی: `src/app/pay/result/page.tsx`
- هدف: بازخورد مرورگر بعد از بازگشت از درگاه یا flow پرداخت.

## رابط و جریان

پیام موفق/ناموفق، پیام خطا در حالت ناموفق، شماره سفارش و کد پیگیری در صورت وجود؛ لینک بازگشت به منو فقط وقتی slug موجود است. صفحه حالت «در انتظار» مستقل ندارد.

## API و داده

query params ok,msg,slug,n,ref؛ verification واقعی در /api/public/pay/callback.

## قواعد بازسازی

query فقط برای UX است؛ موفقیت هرگز صرفاً از query نتیجه‌گیری نشود؛ endpoint callback نتیجه را verify کند؛ متن message escape شود.

برای schema دقیق و شرط‌های موجود، فایل‌های source و API بالا را بخوان. UI عمومی باید tenant-isolated، RTL و responsive باشد.

## مشخصات سطح پیاده‌سازی

صفحه فقط نتیجه بازگشت مرورگر را قالب‌بندی می‌کند. queryهای واقعی `ok`, `msg`, `slug`, `n`, `ref` هستند؛ `ok === "1"` پیام موفقیت UI را می‌سازد، `n` شماره سفارش، `ref` کد پیگیری و `slug` مقصد بازگشت به منو است. `msg` فقط در حالت ناموفق به کاربر نشان داده می‌شود. URL این صفحه خودش callback درگاه یا مرجع اثبات پرداخت نیست.

تأیید مالی در `GET /api/public/pay/callback` با authority/order/payment ذخیره‌شده و وضعیت برگشتی درگاه انجام می‌شود و سپس کاربر را به این صفحه redirect می‌کند. در بازسازی، متن query را sanitize/escape کن، مقدار غیرمنتظره `ok` را شکست/نامشخص بدان و تنها پس از callback سروری معتبر سفارش را paid در نظر بگیر. شناسه سفارش و نام مشتری/مبلغ حساس را از query اضافه نکن. حالت بدون slug باید همچنان مسیر قابل خروج داشته باشد.
