# رزرو میز سمت مشتری

> مشخصات بازسازی عامل برای صفحه/جریان عمومی یا سیستمی.

- مسیر: `/m/:slug/reserve`
- منبع فعلی: `src/app/m/[slug]/reserve/page.tsx + src/components/reservation-form.tsx`
- هدف: رزرو عمومی مشتری با انتخاب زمان شمسی، نوع رزرو، ظرفیت واقعی و میز آزاد؛ پیش‌پرداخت اختیاری.

## رابط و جریان

روند سه‌مرحله‌ای، هم‌راستا با نمونهٔ Orderino: اطلاعات رزرو (عادی/مناسبت/کاری، تاریخ و ساعت شمسی، تعداد مهمان، نام، موبایل، توضیح)، انتخاب میز آزاد و تأیید نهایی. زمان، ظرفیت و میزهای خالی پیش از انتخاب از سرور خوانده می‌شوند؛ میز در submit دوباره با قفل دیتابیس اعتبارسنجی می‌شود. صفحه `/m/:slug/reserve` فقط با feature reservations و تنظیم enabled ارائه می‌شود.

گام انتخاب میز از کارت‌های دو ستونهٔ تصویری استفاده می‌کند: نام میز، شمای گرد/مستطیلی میز و صندلی متناسب با ظرفیت، ظرفیت، بخش/زون میز و وضعیت پیش‌پرداخت در یک کارت انتخاب تکی قرار می‌گیرند. شمار میزهای آزاد کنار عنوان می‌آید و دکمه‌های بازگشت/ادامه در نوار چسبان پایین فرم می‌مانند تا فهرست بلند میزها استفاده‌پذیر باشد. قاب فرم عمومی در دسکتاپ حداکثر ۵۱۲ پیکسل عرض دارد.

## API و داده

GET/POST `/api/public/:slug/reservations`; `GET` جدول‌های available و با ظرفیت کافی را برای `startsAt` و `guestCount` می‌دهد؛ `POST` `reservationType` و `tableId` را نیز می‌گیرد. Jalali input از `PersianDateInput` مشترک است؛ منبع تنظیمات public از `getPublicMenu` می‌آید.

## قواعد بازسازی

timezone Asia/Tehran؛ تداخل میز/ظرفیت، حداقل زمان و مبلغ deposit server-side؛ confirmation SMS بر اساس وضعیت backend؛ تاریخ ورودی normalize شود.

برای schema دقیق و شرط‌های موجود، فایل‌های source و API بالا را بخوان. UI عمومی باید tenant-isolated، RTL و responsive باشد.

## مشخصات سطح پیاده‌سازی

### فرم و مقادیر

فرم فقط در صورت entitlement و `settings.reservations.enabled` فعال است. فیلدها: نام (اجباری، ۲ تا ۸۰ نویسه)، موبایل (اجباری)، تعداد مهمان (۱ تا ۳۰، پیش‌فرض ۲)، تاریخ/ساعت شمسی با `PersianDateInput`، توضیح اختیاری تا ۳۰۰ نویسه. مدت رزرو در تنظیمات رستوران است. وقتی پیش‌پرداخت لازم باشد مبلغ قابل نمایش برابر تعداد مهمان × مبلغ هر نفر است؛ مقدار نمایش‌داده‌شده اطلاع‌رسانی است و سرور آن را دوباره محاسبه می‌کند.

### ارسال و حالت نهایی

گام نخست `startsAt` را به ISO تبدیل و پارامتر زمان/تعداد مهمان را به GET می‌فرستد؛ سپس میز با `tableId` به POST ارسال می‌شود. پاسخ شامل شناسه، میز، نوع رزرو و مبلغ پیش‌پرداخت است؛ صفحه کد پیگیری نشان می‌دهد و صریح می‌گوید درخواست ثبت‌شده رزرو تأییدشده نیست. در صورت مبلغ deposit، قطعی شدن پس از هماهنگی/ثبت وجه است؛ بدون deposit نیز تأیید ظرفیت با رستوران است. خطای API کنار فرم می‌ماند، submit busy/disabled است و با موفقیت فرم جایگزین خلاصه می‌شود.

### قواعد و معیار پذیرش

جلوگیری از رزرو گذشته، ساعت بسته، ظرفیت/تداخل و محاسبه سپرده سمت سرور است. `createReservation` تمام سطرهای میزهای همان کسب‌وکار را در transaction قفل می‌کند، وضعیت/ظرفیت/تداخل را دوباره می‌سنجد و در صورت رقابت درخواست 409 می‌دهد. رزروهای `requested` و `confirmed` ظرفیت را در طول مدت تنظیم‌شده نگه می‌دارند. نوع رزرو به‌صورت `normal|occasion|business` ذخیره می‌شود. API درخواست عمومی rate limit دارد؛ مسیر نمونه `niloofar` نیز همین entitlement، تنظیم رزرو، محدودکننده و اعتبارسنجی tenant را اجرا می‌کند و فقط محدودیت read-only سفارش‌ها را حفظ می‌کند. ارسال SMS تایید/رد با جریان مدیریت رزرو انجام می‌شود، نه فرم عمومی.

Migration افزایشی `0049_reservation_type.sql` مقدار پیش‌فرض `normal` را روی داده‌های قبلی اعمال می‌کند؛ rollback `0049_reservation_type.down.sql` ستون را حذف می‌کند و برچسب نوع رزروهای ثبت‌شده پس از deploy را از دست می‌دهد. migration در این تغییر روی DB اجرا نشده است.

### کارت‌های انتخاب میز — ۲۰۲۶-۱۰-۲۵

- کارت هر میز نمای گرافیکی گرد (ظرفیت تا ۴) یا مستطیلی (ظرفیت بالاتر) دارد و تعداد صندلی‌های نمایشی با ظرفیت هماهنگ می‌شود (حداکثر ۱۲ نماد برای چیدمان‌های بزرگ)؛ کارت اطلاعات نام، ظرفیت و `zone` را در کنار آن نشان می‌دهد.
- برچسب مبلغ کارت، هزینهٔ مستقل میز نیست: اگر پیش‌پرداخت فعال باشد مبلغ کل پیش‌پرداخت همان رزرو (تعداد مهمان × مبلغ تنظیم‌شده برای هر مهمان) نمایش داده می‌شود؛ در غیر این صورت کارت «رایگان» نشان می‌دهد. کد فعلی دادهٔ هزینهٔ اختصاصی هر میز ندارد.
- انتخاب همچنان تکی است و `tableId` همان قرارداد قبلی GET/POST را دارد. API و داده عوض نشده‌اند؛ قفل، ظرفیت و کنترل تداخل در سرور حفظ شده‌اند.
- نوار دکمه‌های پایین هنگام مرور میزهای زیاد در دسترس می‌ماند و شبکهٔ دو ستونه در موبایل نیز قابل استفاده است.
