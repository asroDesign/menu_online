# سفارش‌گیر گارسون

> مشخصات بازسازی ماژول `waiter` برای عامل پیاده‌سازی. این سند رفتار و قرارداد ماژول فعلی را خلاصه می‌کند؛ اگر اختلافی با کد زنده وجود داشت، کد و API فعلی منبع حقیقت هستند.

## جایگاه و دسترسی

- مسیر پنل: `/dashboard/waiter`
- کامپوننت/منبع فعلی: `src/modules/waiter.tsx — Waiter در mode=waiter`
- entitlement تعرفه: `cashier_pos`
- هدف: ثبت سریع سفارش میز توسط گارسون در موبایل و تبلت.

## رابط و جریان کار

رابط دو/سه‌ستونه responsive: دسته‌بندی و جست‌وجوی منو، کارت/افزودن محصول، سبد جاری؛ انتخاب نوع سفارش و میز از modal در ستون سفارش؛ تعداد و یادداشت سفارش؛ دکمه ثبت همیشه در دسترس، در موبایل نوار/پنل پایین. گارسون فقط سفارش را ثبت و توضیح اضافه می‌کند.

پوستهٔ مشترک داشبورد برای نقش‌های `waiter` و `cashier` یک دکمهٔ شناور «ثبت فاکتور» نشان می‌دهد؛ مقصد برای گارسون `/dashboard/waiter` است تا فقط جریان ثبت سفارش بدون تسویه در دسترس باشد. این میان‌بر عمداً در خود `/dashboard/waiter` و `/dashboard/cashier` پنهان است تا با اکشن ثبت داخل میزکارها تکرار نشود. پیاده‌سازی شرط مسیر، نقش و مقصد در `src/components/dashboard-shell.tsx` است.

### بازطراحی رابط گارسون — ۲۰۲۶-۱۰-۲۲

- این تغییر فقط به `mode="waiter"` محدود است؛ حالت `mode="cashier"` ظاهر و جریان سفارش‌گیر صندوق جداگانه حفظ می‌کند.
- سربرگ مینیمال و کم‌ارتفاع فقط عنوان، وضعیت میز و شمار قلم‌ها را نشان می‌دهد؛ توضیح و برچسب فرعی در کارت سربرگ نمایش داده نمی‌شوند. در موبایل و تبلت دکمه انتخاب/تغییر میز بالای فهرست باقی می‌ماند؛ در نمایش عریض انتخاب میز از کارت سفارش جاری استفاده می‌شود.
- فهرست محصول در موبایل دو ستون، تبلت سه ستون و نمایشگر عریض سه تا چهار ستون دارد. کارت محصول تصویر، نام، قیمت، نشان محصول ویژه/آپشن یا وزن و کنترل لمسی افزودن/تعداد را کنار هم نمایش می‌دهد. دسته‌بندی‌ها افقی و قابل پیمایش‌اند.
- تا عرض کمتر از ۱۲۸۰ پیکسل، سبد جاری در نوار ثابت پایین صفحه با تعداد اقلام، نام میز و مبلغ باز می‌شود و پنل آن قابل پیمایش است؛ فضای safe-area رعایت می‌شود. از عرض ۱۲۸۰ پیکسل سبد به ستون کناری ثابت تبدیل می‌شود و کاتالوگ به‌صورت مستقل پیمایش می‌شود.
- فایل ظاهر مستقل `src/modules/waiter-workspace.css` است؛ `cashier-workspace.css` و قواعد صندوق برای این بازطراحی تغییر نکرده‌اند. منطق ثبت سفارش، انتخاب آپشن و وزن، انتخاب میز، یادداشت آشپزخانه و قرارداد API دست‌نخورده مانده است.

## داده و API

GET /api/products, /api/categories, /api/tables, /api/staff, /api/business, /api/r/zones؛ POST /api/orders؛ GET `/api/scales` فقط هنگام بازبودن انتخاب محصول وزنی و داشتن entitlement scale؛ GET /api/public/:slug/customer و /discount فقط در mode صندوق، نه گارسون.

## قواعدی که بازنویسی باید حفظ کند

mode=waiter نباید روش پرداخت/کد تخفیف/دریافت وجه نشان دهد؛ نوع و میز لازم طبق نوع سفارش؛ قیمت client trusted نیست؛ سرور باید قیمت فعلی را محاسبه کند؛ کنترل نقش در API.

- وضعیت‌های loading، خطا، داده خالی و موفقیت را جدا و قابل فهم نشان بده؛ خطا را با امکان تلاش مجدد مدیریت کن.
- رابط فارسی و RTL، ارقام فارسی، پول تومان، و تاریخ‌های شمسی را مطابق ابزارهای مشترک پروژه نمایش بده.
- layout را برای موبایل/تبلت/دسکتاپ بازسازی کن؛ فرم‌ها و جدول‌ها در عرض کم قابل استفاده بمانند و اکشن اصلی از دسترس خارج نشود.
- عملیات را با componentهای مشترک `src/components/ui.tsx`, `src/components/resource-page.tsx` و `src/lib/api.ts` هم‌راستا کن؛ بعد از mutation فهرست/cache را تازه کن.
- tenant isolation، احراز هویت، entitlement و نقش باید سمت API نیز enforce شود؛ مخفی کردن دکمه به‌تنهایی مجوز نیست.

## مشخصات سطح پیاده‌سازی

### سبد و انتخاب میز

داده اولیه از محصولات، دسته‌ها، میزها (poll 10s)، کارکنان و کسب‌وکار می‌آید. فقط محصول `isAvailable` در کاتالوگ سفارش‌گیر دیده می‌شود؛ فیلتر دسته فعال و جست‌وجوی نام است. cart یک map از productId به quantity و سقف هر قلم ۵۰ است؛ صفر کردن quantity قلم را حذف می‌کند. پنل «سفارش جاری» انتخاب میز/نوع سفارش را با modal جست‌وجو دارد؛ گزینه‌ها میزهای واقعی، بیرون‌بر و اگر feature مجاز باشد ارسال‌اند. در میز اشغال‌شده، کاربر می‌تواند `appendTo` همان order را روشن/خاموش کند؛ انتخاب میز از modal باید به sheet قبلی برگردد.

### دسترسی mode گارسون

در mode=`waiter` فقط سفارش ثبت می‌شود. کنترل روش پرداخت، کد و تخفیف دستی، cashback و داده‌های تسویه نمایش داده نشوند؛ نام مشتری/یادداشت آشپزخانه و انتخاب waiter موجود ممکن است نمایش داده شود. UI را برای touch طراحی کن: دکمه‌های کم/زیاد حداقل 44px و دکمه ثبت در footer sticky و safe-area پایین موبایل. اطلاعات محصول/سبد باید در tablet landscape و mobile portrait قابل پیمایش باشند.

POST `/api/orders` payload شامل itemهای `productId,quantity`, `type`, `tableId`, customer, note, `waiterId`, `source=waiter`, `appendTo` است. Server route role waiter را از session می‌شناسد و `waiterId` را خودش override می‌کند. در صورت نبود قلم یا میز/type لازم، inline error/toast و حفظ cart.

اگر `sellingMode=weight` انتخاب شود، modal وزن ناخالص/ظرف می‌گیرد؛ در صورت entitlement ترازو، endpoint tenant-bound `/api/scales` فقط قرائت‌های تازه را بدون device code می‌دهد تا اپراتور یکی را دستی تأیید کند. cart باید مقدار gross را در payload بگذارد و مقدار net را جدا برای نمایش نگه دارد. قیمت هر کیلو و yield را server از محصول می‌خواند. توضیح کامل در [راهنمای فروش وزنی](weighted-sales.md) است.

کارت محصول `imageUrl` محصول را با `ProductThumb` نمایش می‌دهد؛ تصویرهای بارگذاری‌شده از `/api/files/:id` در هر دو mode گارسون و صندوق دیده می‌شوند. fallback تصویری مخصوص صندوق فقط برای محصول بدون تصویر یا تصویر seed قدیمی (`/food/`) است و نباید URL تصویر بارگذاری‌شدهٔ واقعی را جایگزین کند. در خطای تصویر، نماد محصول fallback می‌شود.

**پذیرش:** بدون انتخاب میز submit باید modal را باز کند؛ submit دوبار ممکن نباشد؛ پس از ثبت موفق سبد و note/name پاک و میزها reload شوند؛ خطای server سبد را پاک نکند.

قیمت صفر/نامعتبر از کارت محصول و افزودن variant/وزن پذیرفته نمی‌شود؛ با toast اعلام و cart دست‌نخورده می‌ماند. در صورت تغییر قیمت همزمان در سرور، POST سفارش به‌کمک بررسی مرجع در `createOrder` رد می‌شود. این رفتار برای modeهای گارسون و صندوق از یک کامپوننت مشترک است.

## مرجع بازسازی

برای جزئیات دقیق فیلدها، ترتیب کنترل‌ها، پیام‌های فارسی و قرارداد typeها، فایل منبع بالا را همراه API route متناظر در `src/app/api` بخوان. این راهنما رفتار را مشخص می‌کند و جایگزین بررسی source-of-truth نیست.
