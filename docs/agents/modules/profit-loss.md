# سود و زیان

> مشخصات بازسازی ماژول `profit-loss` برای عامل پیاده‌سازی. این سند رفتار و قرارداد ماژول فعلی را خلاصه می‌کند؛ اگر اختلافی با کد زنده وجود داشت، کد و API فعلی منبع حقیقت هستند.

## جایگاه و دسترسی

- مسیر پنل: `/dashboard/profit-loss`
- کامپوننت/منبع فعلی: `src/modules/finance.tsx — ProfitLoss`
- entitlement تعرفه: `profit_loss`
- هدف: گزارش درآمد، هزینه و سود در بازه زمانی.

## رابط و جریان کار

گزینش بازهٔ ۷/۱۴/۳۰ روز؛ خلاصه درآمد، هزینه، سود/زیان و نمودار روند روزانه؛ نمایش منفی با رنگ/علامت واضح. کارت «ترکیب هزینه‌ها» نمودار دایره‌ای SVG، مجموع هزینه، سهم درصدی و مبلغ هر دسته را نشان می‌دهد. فهرست legend در ارتفاع محدود اسکرول می‌شود تا دسته‌های زیاد صفحه را بلند نکنند؛ داده‌های صفر یا منفی از نمودار حذف می‌شوند.

## داده و API

`GET /api/r/report_pnl?days=n` مقدار `expenseBreakdown: {name, amount}[]` را به تفکیک دسته می‌دهد. برای ثبت‌های حساب‌محور، نام حساب معین هزینه بر `transactions.category` مقدم است؛ برای داده‌های قدیمی بدون حساب، مقدار ذخیره‌شدهٔ دسته و سپس «سایر» استفاده می‌شود. گروه‌بندی سمت سرور tenant-scoped است و بازهٔ انتخابی همان بازهٔ گزارش را کنترل می‌کند.

## قواعدی که بازنویسی باید حفظ کند

تعریف هر سطر طبق aggregation server؛ زیان مقدار منفی را درست نمایش دهد؛ فیلتر بازه یکسان با گزارش فروش.

- وضعیت‌های loading، خطا، داده خالی و موفقیت را جدا و قابل فهم نشان بده؛ خطا را با امکان تلاش مجدد مدیریت کن.
- رابط فارسی و RTL، ارقام فارسی، پول تومان، و تاریخ‌های شمسی را مطابق ابزارهای مشترک پروژه نمایش بده.
- layout را برای موبایل/تبلت/دسکتاپ بازسازی کن؛ فرم‌ها و جدول‌ها در عرض کم قابل استفاده بمانند و اکشن اصلی از دسترس خارج نشود.
- عملیات را با componentهای مشترک `src/components/ui.tsx`, `src/components/resource-page.tsx` و `src/lib/api.ts` هم‌راستا کن؛ بعد از mutation فهرست/cache را تازه کن.
- tenant isolation، احراز هویت، entitlement و نقش باید سمت API نیز enforce شود؛ مخفی کردن دکمه به‌تنهایی مجوز نیست.

## مشخصات سطح پیاده‌سازی

پیش‌فرض ۳۰ روز با selector ۷/۱۴/۳۰؛ GET `/api/r/report_pnl?days=n`. پاسخ revenue, discounts, tax, cogs, grossProfit, expenses, otherIncome, net, expenseBreakdown, series روزانه و cogsCoverage. صورت: فروش خالص (پس از تخفیف، بدون مالیات)، منفی COGS همراه پوشش recipe، gross profit، منفی هزینه عملیاتی، positive other income و net. سود خالص رنگ سبز و زیان قرمز. نمودار `revenue-cogs-expenses` روزانه؛ sidebar composition expense categories.

به علت نبود recipe برای همه محصولات، `cogsCoverage` باید آشکار بماند تا مدیر بداند estimate کامل نیست. Server aggregation تعریف اعداد را تعیین می‌کند؛ UI نباید revenue را دوباره از total سفارش بسازد یا tax را سود فرض کند. سریالی خالی، expense breakdown خالی، سود/زیان منفی و null data حالت‌های مجزا هستند.

**پذیرش:** ۷/۱۴/۳۰ روز، هزینه صفر، net منفی، COGS coverage پایین، داده خالی و format پول/تاریخ.

## اپ Windows آفلاین

نمای آفلاین فقط یک snapshot ۹۰روزهٔ read-only در تب گزارش‌ها است. entitlementهای `cashier_pos` و `profit_loss` لازم‌اند. فروش آفلاین هنوز sync‌نشده در آن نیست. برای حفظ هزینه/درآمد تاریخی، COGS از `orders.cogs` ذخیره‌شده می‌آید، نه محاسبهٔ دوبارهٔ recipe فعلی؛ UI پوشش COGS را نشان می‌دهد. این view معادل گزارش آنلاین یا جایگزین دفتر کل نیست و بازهٔ دلخواه، ریز تراکنش، print/export و ثبت mutation را پوشش نمی‌دهد. سقف امن: ۵۰٬۰۰۰ سفارش، ۲۰٬۰۰۰ تراکنش و snapshot کلی ۴MB. [گزارش تغییر آفلاین](../../updates/2026-10-27-offline-profit-loss-report.md).

## مرجع بازسازی

برای جزئیات دقیق فیلدها، ترتیب کنترل‌ها، پیام‌های فارسی و قرارداد typeها، فایل منبع بالا را همراه API route متناظر در `src/app/api` بخوان. این راهنما رفتار را مشخص می‌کند و جایگزین بررسی source-of-truth نیست.
