# فروش وزنی محصولات

> راهنمای بازسازی و توسعه قابلیت M09. این راهنما رفتار فعلی checkout را ثبت می‌کند؛ مسیر انبار/حسابداری و migrationهای اعمال‌نشده را کامل یا deployشده فرض نکن.

## هدف و جایگاه

فروش محصولات با واحد وزنی را برای محصولاتی مثل گوشت یا مواد فله‌ای فراهم می‌کند. قیمت کاتالوگِ این نوع محصول قیمت هر کیلوگرم به تومان است. کاربر وزن ناخالص و ظرف را وارد می‌کند یا در صندوق/گارسون یک قرائت تازه‌ی ترازو را انتخاب می‌کند؛ مبلغ بر پایه وزن خالص حساب می‌شود. کارکرد بین محصولات، منوی عمومی، کیوسک، گارسون، صندوق، رسید، گزارش و مصرف رسپی تقسیم شده است و صفحه داشبورد مستقل ندارد.

## دسترسی و محصول

ویرایش محصول از `/dashboard/products` انجام می‌شود. همان guard فعلی محصولات (مدیر کسب‌وکار) حاکم است. فیلدهای تازه:

- `sellingMode`: `count` پیش‌فرض برای محصولات قبلی، یا `weight`.
- `price`: برای `count` قیمت هر عدد و برای `weight` قیمت هر کیلوگرم.
- `yieldRatio`: نسبت وزن پخته/فروشی به خام، بازه `(0,1]` و مقدار پیش‌فرض `1`. مثلاً `.8` یعنی برای ۱ کیلو محصول پخته، ۱٫۲۵ کیلو ماده خام در رسپی مصرف می‌شود.

برای محصول وزنی گروه modifier فعال پذیرفته نمی‌شود، چون فعلاً نرخ واحد محصول مبنای محاسبه است. اعتبارسنجی update، مقدار فعلی محصول را هم می‌خواند تا تغییر نام یا توضیح، محصول وزنی دارای modifier قبلی را بی‌صدا از کنترل خارج نکند.

## جریان سفارش

انتخاب محصول وزنی در منوی مشتری، کیوسک و صندوق/گارسون modal وزن را باز می‌کند. وزن ناخالص و ظرف به گرم صحیح وارد می‌شود؛ وزن ظرف باید از ناخالص کمتر باشد. modal وزن خالص و قیمت نهایی را نشان می‌دهد. در گارسون/صندوق، اگر ترازو با entitlement `scale` تازه باشد، اپراتور می‌تواند قرائت را با کلیک صریح به فیلد منتقل کند. در منوی عمومی/کیوسک وزن دستی باقی می‌ماند.

`POST /api/orders` و مسیرهای ثبت سفارش عمومی/کیوسک وزن را به گرم می‌فرستند. `quantity` همچنان تعداد بسته/ردیف سفارش و صحیح است؛ برای هر کدام از حداکثر ۵۰ قلم، سرور قیمت و `yieldRatio` جاری محصول را از همان tenant می‌خواند، سپس خودش gross−tare، گردکردن مبلغ و `lineTotal` را محاسبه می‌کند. هیچ مبلغ یا نرخ ارسالی مرورگر مبنا نیست. وزن ذخیره‌شده در `order_items.weight_grams` وزن خالص فروخته‌شده است؛ `tare_grams` و `yield_ratio_snapshot` هم نگه داشته می‌شوند.

فرمول مبلغ: `round(netGrams * currentPricePerKg / 1000)`. سقف وزن هر ردیف ۱۰۰٬۰۰۰ گرم است؛ مبلغ کل سفارش باید در محدوده integer دیتابیس بماند. با تغییر قیمت/بازده محصول بعد از ثبت سفارش، رسید و مصرف مواد از snapshot سفارش استفاده می‌کنند.

## اتصال ترازو

Agent در `public/bridge/agent.mjs` واحد تنظیمی g را به kg نرمال می‌کند و device API مقدار را در `devices.last_value` ذخیره می‌کند. `GET /api/scales` فقط دستگاه‌های scale tenant جاری با heartbeat حداکثر ۲۰ ثانیه و وزن معقول را به صورت `{id,name,weightGrams,lastSeenAt}` برمی‌گرداند؛ `code` محرمانه‌ی دستگاه را برنمی‌گرداند. UI صندوق/گارسون هر ۲٫۵ ثانیه، فقط تا وقتی modal کالای وزنی باز است، قرائت‌ها را تازه می‌کند. انتخاب قرائت یک اقدام تأییدی اپراتور است.

قرائت، گواهی امضاشده یا قفل‌شده به سفارش نیست؛ اپراتور می‌تواند وزن را دستی وارد کند و مقدار ارسال‌شده‌ی client همچنان می‌تواند دستکاری شود. سرور نرخ را معتبر می‌کند، ولی صحت وزن فیزیکی را از دستگاه تضمین نمی‌کند. اگر وزن باید از نظر مالی فقط به قرائت سخت‌افزاری محدود شود، باید پروتکل نمونه‌ی یکتای امضاشده/مصرف‌شونده و سیاست پایش پایداری پیش از فعال‌سازی ساخته شود. API فعلی فقط آخرین نمونه را نگه می‌دارد.

## انبار، گزارش و رسید

در settle سفارش، برای ردیف وزنی ضریب پایه‌ی رسپی برابر `quantity * (netWeightGrams / 1000) / yieldRatioSnapshot` است؛ `recipes.quantity` مقدار ماده خام لازم به‌ازای یک کیلو محصول فروشی تعریف می‌شود. موجودی، گردش sale، COGS و سند فروش در همان مسیر transactional موجود ثبت می‌شوند. گزارش فروش و دسته‌بندی از `order_items.line_total` استفاده می‌کنند، نه `price * quantity` که برای فروش وزنی قیمت هر کیلو است. رسید چاپی و modal سفارش وزن خالص/ظرف و مبلغ ردیف را نمایش می‌دهند.

قبل از تعریف رسپی برای محصول وزنی، واحد ماده اولیه را با «کیلوگرم خام برای هر کیلو محصول پخته» تنظیم کن؛ واحد و تبدیل خودکار g/kg در ردیف recipe هنوز در UI اجباری نشده است. بازپرداخت یا برگشت فیزیکی پس از تسویه باید از جریان برگشت موجودی/حسابداری idempotent عبور کند؛ تغییر status سفارش به canceled به تنهایی اثبات refund نیست و این سناریو در migration/feature جدید پیاده‌سازی نشده است.

## Schema و migration

`products.selling_mode`, `products.yield_ratio`, `order_items.weight_grams`, `tare_grams`, `yield_ratio_snapshot`, `line_total` در `src/db/schema.ts` آمده‌اند. migration افزایشی `0022_weighted_sales.sql` مقدارهای قدیمی را به count/ratio=1 و line total بر اساس price×quantity backfill می‌کند؛ اگر ردیف تاریخی از سقف integer خارج باشد migration را با خطای روشن متوقف می‌کند. فایل `0022_weighted_sales.down.sql` پیش از پذیرفتن سفارش وزنی قابل استفاده است؛ پس از ایجاد سفارش وزنی، اجرای down موجب از دست‌رفتن snapshot وزن می‌شود. این migration در این checkout اجرا نشده است.

## فایل‌های اصلی و تست

- `src/lib/weighted-sales.ts`: محاسبه/اعتبارسنجی خالص، مبلغ، بازده و سازگاری line total.
- `src/lib/order-cart.ts`: سبد محلی. `weightGrams` خروجی آن gross است تا backend tare را دقیقاً یک بار کم کند؛ `netWeightGrams` فقط برای نمایش UI است.
- `src/lib/orders.ts`, `src/lib/resources.ts`, `src/app/api/scales/route.ts`: قیمت authoritative، validation و endpoint قرائت تازه.
- `src/components/product-option-picker.tsx`, `src/modules/waiter.tsx`, `src/components/menu-client.tsx`, `src/components/kiosk-client.tsx`, `src/app/dashboard/products/page.tsx`: UI ثبت وزن/تنظیم محصول.
- `src/app/print/receipt/[id]/page.tsx`, `src/modules/orders.tsx`, `src/app/api/stats/route.ts`, `src/lib/registry-b.ts`, `src/lib/accounting.ts`: رسید، گزارش و هزینه مصرف.
- `tests/security-regressions.test.cjs`: ۲۵۰ گرم از نرخ ۱۰۰٬۰۰۰ برابر ۲۵٬۰۰۰؛ ظرف، بازده و mode نامعتبر رد؛ yield=.8 اثر مواد خام را حفظ می‌کند؛ سبد gross را برای backend و net را برای نمایش جدا می‌کند.

فرمان‌های بررسی: `npm run typecheck` و `node --test tests/security-regressions.test.cjs`. تست integration با PostgreSQL و اجرای migration هنوز انجام نشده است.
