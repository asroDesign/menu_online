# سفارش‌ها

> مشخصات بازسازی ماژول `orders` برای عامل پیاده‌سازی. این سند رفتار و قرارداد ماژول فعلی را خلاصه می‌کند؛ اگر اختلافی با کد زنده وجود داشت، کد و API فعلی منبع حقیقت هستند.

## جایگاه و دسترسی

- مسیر پنل: `/dashboard/orders`
- کامپوننت/منبع فعلی: `src/modules/orders.tsx — Orders`
- entitlement تعرفه: `cashier_pos`
- هدف: صندوق مرکزی مشاهده، پیگیری و مدیریت همه سفارش‌های رستوران.

## رابط و جریان کار

لیست زنده با polling هشت‌ثانیه‌ای؛ فیلتر فعال/همه/وضعیت/بایگانی، جست‌وجوی شماره و میز و مشتری؛ کارت هر سفارش با اقلام، یادداشت، نوع سفارش، منبع و وضعیت. جزئیات در modal باز می‌شود و عملیات وضعیت، چاپ رسید/فاکتور، بررسی پرداخت، ارسال مبلغ به کارتخوان و اتصال پیک را ارائه می‌کند. بایگانی حذف‌شده فقط برای مدیر و امکان بازیابی دارد.

## داده و API

GET /api/orders?limit=300؛ برای حذف‌شده‌ها GET /api/orders?deleted=true&limit=300؛ GET /api/staff؛ GET /api/r/couriers؛ PATCH /api/orders/:id (وضعیت/پیک/بازیابی)؛ POST /api/r/posrequests (درخواست کارتخوان).

## قواعدی که بازنویسی باید حفظ کند

حذف باید نرم باشد؛ وضعیت و مبلغ نهایی را سرور تعیین می‌کند؛ نمایش/عملیات بر اساس role محدود شود؛ بعد از mutation فهرست تازه شود؛ نمایش تاریخ شمسی و ارقام فارسی.

- وضعیت‌های loading، خطا، داده خالی و موفقیت را جدا و قابل فهم نشان بده؛ خطا را با امکان تلاش مجدد مدیریت کن.
- رابط فارسی و RTL، ارقام فارسی، پول تومان، و تاریخ‌های شمسی را مطابق ابزارهای مشترک پروژه نمایش بده.
- layout را برای موبایل/تبلت/دسکتاپ بازسازی کن؛ فرم‌ها و جدول‌ها در عرض کم قابل استفاده بمانند و اکشن اصلی از دسترس خارج نشود.
- عملیات را با componentهای مشترک `src/components/ui.tsx`, `src/components/resource-page.tsx` و `src/lib/api.ts` هم‌راستا کن؛ بعد از mutation فهرست/cache را تازه کن.
- tenant isolation، احراز هویت، entitlement و نقش باید سمت API نیز enforce شود؛ مخفی کردن دکمه به‌تنهایی مجوز نیست.

## مشخصات سطح پیاده‌سازی

### فهرست

- تب‌ها: «فعال»، «همه»، سپس همه statusهای `ORDER_STATUSES`؛ برای owner/manager تب «حذف‌شده‌ها» اضافه می‌شود. polling هر ۸ ثانیه و limit برابر ۳۰۰ است. شمارش تب‌ها از داده‌ی همان query ساخته می‌شود؛ شمارش وضعیت‌های بایگانی نباید با سفارش‌های عادی قاطی شود.
- جست‌وجو شماره سفارش (با normalize رقم فارسی)، نام میز و نام مشتری را پوشش می‌دهد. کارت سفارش شماره/ساعت نسبی، status، نوع/میز، source، پیش‌سفارش، وضعیت پرداخت، وضعیت delivery، حداکثر ۳ قلم اول، note، waiter/customer و total را دارد.
- container فهرست خودش scroll عمودی دارد؛ grid از یک ستون موبایل تا چهار ستون دسکتاپ می‌رود. وضعیت loading، خطا با retry و empty برای بایگانی/فیلتر/کل فهرست پیام‌های جدا دارند.

### جزئیات و mutation

modal جزئیات، خطوط سفارش، subtotal، discount، delivery fee، cashback، tax، service و total را نشان می‌دهد؛ نیز یادداشت، آدرس، تماس، نقشه، ساعت برنامه‌ریزی، مشتری و زمان را. مدیر می‌تواند حذف نرم کند؛ در تب بایگانی زمان/نام حذف‌کننده و action بازگردانی نمایش داده می‌شود. عملیات ثبت‌شده: پیشبرد status، لغو، تأیید پرداخت کارت‌به‌کارت، درخواست مبلغ POS، انتخاب waiter فعال و اختصاص/تعویض courier. برای تحویل ناموفق، `courierNote` و وضعیت `not_home/failed` نمایش داده و سفارش می‌تواند به پیک دیگری برود.

### قواعد backend که UI باید منعکس کند

`GET /api/orders` به `cashier_pos` نیاز دارد و `deleted=true` فقط manager-role؛ POST نرخ ۳۰ درخواست در ۶۰ ثانیه برای هر user/business دارد. POST waiter اگر payment/discount/cashback بفرستد 403 می‌گیرد. status `paid` از PATCH عادی مستقیم set نمی‌شود و از `settleOrder` عبور می‌کند؛ حذف soft است؛ restore فقط مدیر است. روی status از `statusInfo()` و `ORDER_STATUSES` استفاده کن، نه ترتیب دلخواه ثابت. کارت POS فقط request می‌سازد؛ موفقیت پرداخت تا تأیید جداگانه رخ نداده.

**پذیرش:** جست‌وجوی فارسی، scroll فهرست، بازشدن modal، soft-delete و restore؛ نقش chef/waiter/cashier؛ card-to-card pending؛ delivery assigned/picked-up/delivered/failure؛ جلوگیری از double-submit و refresh بعد از mutation.

## مرجع بازسازی

برای جزئیات دقیق فیلدها، ترتیب کنترل‌ها، پیام‌های فارسی و قرارداد typeها، فایل منبع بالا را همراه API route متناظر در `src/app/api` بخوان. این راهنما رفتار را مشخص می‌کند و جایگزین بررسی source-of-truth نیست.
