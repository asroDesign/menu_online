# دفتر چک

## کاربرد و نقش

ماژول `/dashboard/cheques` چک‌های دریافتنی و پرداختنی را ثبت می‌کند، سررسیدشان را در تقویم شمسی نشان می‌دهد، تغییر وضعیت‌ها را نگه می‌دارد و برای ثبت، تسویه یا اصلاح وضعیت سند حسابداری دوطرفه می‌سازد. دفتر به بانک، صیاد یا پرداخت واقعی وصل نیست. entitlement آن `cheque_register` است و API فقط مدیر و accountant را می‌پذیرد.

## فایل‌ها و API

- UI: `src/modules/cheques.tsx`; routeهای API: `src/app/api/cheques/route.ts` و `src/app/api/cheques/accounts/route.ts`.
- قواعد خالص وضعیت و ردیف سند: `src/lib/cheques.ts`; سرفصل‌ها و ثبت سند اتمی: `src/lib/accounting.ts`.
- داده: جدول‌های `cheques`, `cheque_events`, `acc_accounts`, `acc_documents`, `acc_lines` در `src/db/schema.ts`.
- مهاجرت‌ها: `0020_cheque_register.sql` (دفتر)، `0026_cheque_updated_at.sql` (ستون زمان اصلاح) و `0027_cheque_accounting.sql` (وضعیت‌ها و پیوند دفتر کل). برای نسخه جدید باید مهاجرت ۰۰۲۷ پیش از استفاده اجرا شود.
- `GET /api/cheques` فهرست ۵۰۰ چک آخر کسب‌وکار نشست را می‌دهد. `GET /api/cheques?year=<سال شمسی>&month=<1..12>` فقط سررسیدهای همان ماه را تا ۵۰۰۰ ردیف می‌دهد. رویدادها و چک‌ها tenant-scoped هستند.
- `GET /api/cheques/accounts` حساب‌های فعال معین و تفصیلی همان کسب‌وکار را برای انتخاب کد طرف سند می‌دهد؛ دو حساب کنترلی چک از انتخاب حذف‌اند.
- `POST /api/cheques` جهت، مبلغ مثبت، سررسید، و `accountingAccountId` را لازم دارد. شناسه حساب باید فعال، tenant-owned و معین/تفصیلی باشد. چک در وضعیت `registered` ایجاد می‌شود؛ ردیف چک، سند پایه و event اولیه در یک تراکنش ذخیره می‌شوند.
- `PATCH /api/cheques` بدنه `{id,status,requestKey,note?,accountingAccountId?,statusAccountId?}` می‌گیرد. `accountingAccountId` برای ساخت سند پایهٔ چک قدیمی است؛ `statusAccountId` حساب مقصدِ واگذاری چک است. کلید درخواست UUID و یکتا در همان کسب‌وکار است؛ چک قفل سطری می‌شود. تکرار همان درخواست پاسخ idempotent می‌گیرد؛ کلید یکسان برای چک دیگر رد می‌شود.

## وضعیت‌های قابل انتخاب

برچسب‌ها به ترتیب: `registered` = ثبت شد، `passed` = پاس شد، `bounced` = برگشت خورده، `returned` = عودت داده شد، `assigned` = واگذار شد و `voided` = ابطال شد. همه وضعیت‌ها برای چک صادرشده و دریافت‌شده قابل اصلاح‌اند، به جز `assigned` که فقط برای چک دریافتنی است. تغییر به وضعیت فعلی بدون تغییر حساب واگذاری رد می‌شود؛ چک دریافتنی در وضعیت واگذارشده می‌تواند با انتخاب حساب دیگر دوباره واگذار شود.

برای هر انتقال وضعیت، event جدید با actor، یادداشت، حساب طرف، سند اثر وضعیت و سند برگشت (در صورت نیاز) افزوده می‌شود. رویدادهای پیشین پاک یا ویرایش نمی‌شوند. UI شناسه سند پایه و سندهای مربوط به eventها را نشان می‌دهد.

## منطق سند دوطرفه

سرفصل‌های کنترلی خودکار در کدینگ هر کسب‌وکار ساخته می‌شوند: `1202` اسناد دریافتنی چک (دارایی بدهکارطبیعت) و `2105` اسناد پرداختنی چک (بدهی بستانکارطبیعت). اگر کسب‌وکار کدینگ موجود دارد، helper آن‌ها را زیر کل‌های `12` و `21` به شکل idempotent می‌افزاید؛ کد موجود با ساختار ناسازگار یا غیرفعال باعث خطای روشن می‌شود. حساب طرف در فرم انتخاب می‌شود.

| رویداد | بدهکار | بستانکار |
|---|---|---|
| ثبت چک دریافتنی | 1202 اسناد دریافتنی | حساب طرف انتخاب‌شده |
| ثبت چک پرداختنی | حساب طرف انتخاب‌شده | 2105 اسناد پرداختنی |
| پاس چک دریافتنی | 1102 بانک‌ها | 1202 اسناد دریافتنی |
| پاس چک پرداختنی | 2105 اسناد پرداختنی | 1102 بانک‌ها |
| واگذاری چک دریافتنی | حساب واگذاری انتخاب‌شده | 1202 اسناد دریافتنی |
| برگشت/عودت/ابطال چک دریافتنی | حساب طرف سند پایه | 1202 اسناد دریافتنی |
| برگشت/عودت/ابطال چک پرداختنی | 2105 اسناد پرداختنی | حساب طرف سند پایه |

برای سه وضعیت اخیر، جهت دقیق بدهکار/بستانکار معکوس جهت سند پایه است. ثبت `registered` سند تعدیلی ندارد. سند ثبت و سند وضعیت در همان تراکنش تغییر چک ایجاد می‌شوند.

هر سند اثر وضعیت در event ارجاع می‌شود. در انتقال بعدی، اگر وضعیت قبلی سند تعدیلی داشته باشد، route ردیف‌های همان سند را جابه‌جا می‌کند، سند برگشت را می‌سازد و سند قبلی را `reversed` می‌کند؛ سپس سند وضعیت تازه را ثبت می‌کند. این کار همراه update وضعیت و event جدید در یک تراکنش DB انجام می‌شود؛ خطای هر بخش، همه آن تراکنش را rollback می‌کند. `sourceRef`های پایدار `cheque:<id>:initial`, `cheque:<id>:state:<requestKey>` و `cheque:<id>:reverse:<requestKey>` جلوی ثبت تکراری سند را می‌گیرند. اگر سند وضعیت قبلی از صفحه حسابداری جداگانه برگشت خورده باشد، انتقال متوقف می‌شود تا حسابدار مغایرت را بررسی کند.

## چک‌های قدیمی و مهاجرت

مهاجرت ۰۰۲۷ وضعیت‌های قبلی را بدون حذف ردیف‌ها تبدیل می‌کند: issued/received/presented ← registered، cleared ← passed، returned قدیمی ← bounced، canceled ← voided. چون نسخه پیشین سندهای چک ایجاد نکرده، ستون‌های مرجع برای داده‌های قدیمی خالی می‌مانند. هنگام اولین تغییر وضعیت، UI انتخاب کد حساب پایه را لازم می‌کند و API سند پایه و سند وضعیت مقصد را در تراکنش می‌سازد؛ اگر مقصد «واگذار شد» باشد، حساب واگذاری جداگانه انتخاب می‌شود تا حساب اولیه و حساب مقصد با هم اشتباه نشوند. تاریخ ثبت حسابداری برای این تکمیل، تاریخ همان اصلاح است تا سال مالی بسته مسدودش نکند.

Rollback مهاجرت `0027` عمدی no-op است: نگاشت وضعیت‌های جدید به مدل قدیم مبهم است و حذف ارجاع سندها audit trail را می‌شکند. برای بازگشت نسخه، این migration نباید rollback شود؛ نسخه قدیمی که وضعیت‌های جدید را نمی‌شناسد ناسازگار است.

## UI و تقویم

تقویم یک ماه شمسی باز را نشان می‌دهد، هفته از شنبه شروع می‌شود و ماه قبل/بعد و ماه جاری دارد. هر روز جمع چک‌های دریافتی و پرداختنی و تعداد را می‌دهد؛ کلیک روز، فهرست را فیلتر می‌کند. voided از جمع روزانه کنار می‌رود. فهرست کارت‌ها وضعیت، سررسید، حساب پایه، شماره سند، eventها و سند/برگشت هر event را نمایش می‌دهد. modal «تغییر وضعیت» فهرست وضعیت‌های معتبر همان جهت را می‌دهد؛ `assigned` کد حساب واگذاری می‌خواهد.

در modal ثبت چک، فیلد «کد حساب طرف سند» پیش از ثبت لازم است. مبلغ به تومان، تاریخ با `PersianDateInput` و یادداشت اختیاری وارد می‌شود. بعد از ساخت، پیام روشن می‌گوید سند حسابداری خودکار ساخته شده است.

## محدودیت و کنترل

تمام queryها با `auth.business.id` محدودند. `withAuth` اعمال feature و نقش را بر عهده دارد؛ account ID و document ID نیز tenant-scoped هستند. route قیمت یا عملیات بانکی اجرا نمی‌کند. اتصال بانک/صیاد، پرداخت واقعی، reminder، پیامک و reconciliation خودکار پیاده نشده‌اند. هر سند با تاریخ سرور جاری، سال مالی باز، منبع `cheque` و توصیف روشن ثبت می‌شود.

## آزمون و وضعیت اجرا

`tests/security-regressions.test.cjs` قواعد جهت‌دار status، توازن خطوط همه postingها، محدودیت واگذاری به دریافتنی، tenant guard، idempotency، update قفل‌شده، سند/برگشت در تراکنش و migration را بررسی می‌کند. در این نوبت typecheck و lint هدفمند route/helper/schema/UI/test و regression file موفق بودند. تست دیتابیس PostgreSQL اجرا نشد و migration ۰۰۲۷ روی دیتابیس اجرا نشده است؛ قبل از استفاده باید روی دیتابیس محیط اعمال و یکپارچگی balance با DB test اختصاصی نیز سنجیده شود.

پیشینهٔ اصلاح خطای `updated_at` و تقویم ماهانه در دفتر وضعیت ریشه و تغییرات قبلی این سند نگه داشته شده است.
