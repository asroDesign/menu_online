# دفتر چک در اپ Windows آفلاین

## نقش

این vertical slice اجازه می‌دهد مدیر رستوران پس از دریافت snapshot دفتر چک، هنگام قطع شبکه فهرست و جزئیات چک‌های cacheشده را ببیند، چک دریافتنی/پرداختنی جدید ثبت کند و برای چک موجود درخواست تغییر وضعیت بگذارد. فرمان‌های نوشتنی تا اتصال بعدی به‌صورت رمز‌شده در SQLite می‌مانند؛ سند رسمی حسابداری فقط بعد از پذیرش سرور ایجاد می‌شود. این قابلیت ارتباط با بانک، صیاد، کارتخوان یا ارسال پیامک در حالت آفلاین را شبیه‌سازی نمی‌کند.

## پیش‌نیاز و فایل‌ها

- Pairing معتبر Windows و PIN مدیر محلی لازم است. دریافت snapshot و ثبت فرمان به entitlementهای هم‌زمان `cashier_pos`, `cheque_register`, و `accounting` نیاز دارد.
- API snapshot و dispatcher فرمان در `src/lib/offline-dashboard.ts` هستند؛ منطق sync سرور در `src/lib/offline-cheques.ts` است.
- قرارداد محلی، رمزگذاری DPAPI، allowlist و outbox در `windows-bridge/offline-core/src/lib.rs` قرار دارند.
- worker دریافت/ارسال، Tauri commands و registration در `windows-bridge/src-tauri/src/offline.rs` و `windows-bridge/src-tauri/src/main.rs` هستند.
- UI دفتر چک در `windows-bridge/ui/index.html`, `windows-bridge/ui/pos.js`, و `windows-bridge/ui/style.css` پیاده شده است.
- قواعد انتقال وضعیت/سند از `src/lib/cheques.ts` و `src/lib/accounting.ts` مشترک با نسخهٔ آنلاین استفاده می‌شوند.

## دادهٔ cacheشده

`GET /api/offline-dashboard/snapshots/cheques` دادهٔ tenant جاری را می‌گیرد: حداکثر ۵۰۰۰ چک با تاریخ صدور/سررسید، شماره و سریال، بانک/شعبه، بابت، شناسه صیادی، مبلغ، وضعیت و ارجاع سند؛ حداکثر ۱۰۰۰ ذی‌نفع با نام/کد ملی/موبایل؛ حداکثر ۲۰٬۰۰۰ رویداد متعلق به همان چک‌های snapshot؛ حداکثر ۱۰۰۰ حساب فعال معین/تفصیلی قابل انتخاب؛ و فهرست بانک‌ها و «بابت». اگر هر سقف رد شود endpoint با 413 پاسخ می‌دهد و دادهٔ ناقص را ذخیره نمی‌کند. سقف payload عمومی snapshot چهار مگابایت و عمر آن هفت روز است.

اطلاعات هویتی ذی‌نفع و متن یادداشت نیز PII محسوب می‌شوند و snapshot/outbox روی Windows با DPAPI حساب فعلی محافظت می‌شوند. پاسخ 401/403 هنگام اتصال cache دستگاه را پاک می‌کند؛ snapshot منقضی برای مشاهده باقی می‌ماند اما ساخت فرمان را نمی‌پذیرد. این snapshot صفحه‌بندی ندارد؛ برای دفترهای بزرگ‌تر از سقف باید pagination جداگانه طراحی شود.

## گردش UI

- تب «دفتر چک» خلاصهٔ پرداختنی/دریافتنی، تعداد و مبلغ، چک‌های سررسید نزدیک، فیلتر نوع/وضعیت و جست‌وجوی نام، بانک، شماره و سریال را نمایش می‌دهد.
- جزئیات از snapshot محلی خوانده می‌شود: مشخصات چک، اطلاعات ذی‌نفع، حساب سند پایه و رویدادهای وضعیت/شماره سند.
- فرم ثبت، جهت، ذی‌نفع موجود یا اطلاعات ذی‌نفع تازه، شماره و سریال، تاریخ‌های شمسی، بانک/نام بانک سفارشی، شعبه، بابت/شرح آزاد، شناسه صیادی، مبلغ، حساب معین/تفصیلی طرف سند، یادداشت و PIN مدیر را می‌گیرد.
- تغییر وضعیت فقط از مقادیر مجاز در `src/lib/cheques.ts` ارائه می‌شود. `assigned` فقط برای چک دریافتنی است و حساب مقصد جدا می‌خواهد. برای هر چک با فرمان در انتظار یا conflict روی همان snapshot، UI تغییر مجدد را تا snapshot تازه غیرفعال می‌کند.
- وضعیت محلی به عنوان وضعیت قطعی/ثبت‌شده نمایش داده نمی‌شود. فرمان‌های pending، conflict، rejected و synced در صف قابل مشاهده‌اند؛ پس از sync، snapshot تازه وضعیت رسمی را جایگزین می‌کند.

## قرارداد فرمان و یکپارچگی

فرمان‌ها schemaVersion=1، UUID، businessId، `baseDataset=cheques`، UUID/revision snapshot و payload حداقلی دارند. Rust فقط `register` و `set_status` را در outbox رمز‌شده می‌پذیرد؛ PIN، اعتبار snapshot و شناسه‌های حساب/چک را پیش از enqueue بررسی می‌کند. worker هر فرمان را با `POST /api/offline-dashboard/commands` می‌فرستد.

سرور Bearer دستگاه را بازاعتبارسنجی می‌کند؛ terminal قفل می‌شود و tenant فعال، entitlement، UUID/hash، snapshot همان device/business با اعتبار جاری و روابط tenant بررسی می‌شوند. replay همان UUID/hash پاسخ ثبت‌شده را برمی‌گرداند؛ همان UUID با payload متفاوت conflict است. snapshot قدیمی/منقضی نیز conflict می‌شود.

ثبت چک: سرور تاریخ تهران، مبلغ، فیلدهای اجباری، checksum کد ملی، قالب موبایل، وجود ذی‌نفع، شماره/سریال یکتا در کسب‌وکار، فعال بودن حساب معین/تفصیلی و انتخاب‌نشدن حساب کنترلی چک را دوباره بررسی می‌کند. ایجاد ذی‌نفع، چک، سند پایه، event اولیه و command ledger در transaction واحد است. collision یکتای شماره/سریال transaction را rollback می‌کند و پاسخ 409 می‌دهد.

تغییر وضعیت: سطر چک قفل و وضعیت/`updatedAt` فعلی با ردیف snapshot مقایسه می‌شود. helper انتقال وضعیت مشترک اعتبار transition را بررسی می‌کند. حساب‌ها دوباره tenant-scoped و فعال بررسی می‌شوند. اگر سند وضعیت قبلی وجود داشته باشد، سند برگشت ساخته و سند قبلی reversed می‌شود؛ سپس سند وضعیت جدید، update شرطی چک، event و ledger فرمان در همان transaction ثبت می‌شوند. خطا در هر مرحله کل تغییر مالی/وضعیت را rollback می‌کند. تغییر هم‌زمان پاسخ conflict می‌گیرد و worker snapshot را تازه می‌کند.

## محدودیت‌ها

- تاریخچهٔ محلی فقط رکوردهای داخل snapshot محدود را دارد؛ هنگام عبور از سقف، endpoint خطا می‌دهد و سابقهٔ ناقص را وانمود نمی‌کند.
- پیامک یادآوری سررسید تنها در مسیر سرور و طبق تنظیمات جاری ارسال می‌شود؛ در قطعی اینترنت پیامک ارسال یا از روی صف محلی replay نمی‌شود.
- تعریف/ویرایش/حذف ذی‌نفع، ثبت پرداخت بانکی، اتصال بانک/صیاد، دریافت نتیجهٔ تسویه، برنامه‌ریزی SMS و گزارش دفتر چک آفلاین نشده‌اند.
- این ماژول با کد TypeScript و JavaScript بررسی می‌شود، اما کامپایل Rust/Tauri تا فراهم‌بودن `cargo` در محیط تأیید نشده است. دیتابیس، migration یا تست یکپارچه در این تغییر اجرا نمی‌شود.

## تغییرات این نسخه

شرح توسعه، قرارداد API، فایل‌ها، بررسی‌های انجام‌شده و محدودیت اجرا در [گزارش دفتر چک آفلاین](../../updates/2026-10-26-offline-cheques.md) ثبت شده است. برای وضعیت سایر ماژول‌های Windows، [نقشهٔ کامل پنل آفلاین](offline-full-dashboard.md) را ببینید.
