# اتصال سخت‌افزار به نرم‌افزار (پیجر، کارتخوان، پرینتر، تبلت)

نرم‌افزار روی وب اجرا می‌شود و **سرور وب به‌طور مستقیم به دستگاه‌های داخل رستوران دسترسی ندارد** (شبکه‌ی محلی پشت NAT است). بنابراین اتصال همیشه از سمت رستوران به سرور برقرار می‌شود، به یکی از سه روش:

| روش | چیست | مناسب برای |
|---|---|---|
| **۱. مرورگر (Web Serial / چاپ مرورگر)** | صفحه‌ی نرم‌افزار روی رایانه‌ی صندوق باز است و مستقیم با دستگاه USB/Serial حرف می‌زند | فرستنده‌ی پیجر USB، پرینتر با چاپ مرورگر |
| **۲. برنامه‌ی پل (Bridge Agent)** | برنامه‌ی دسکتاپ Rust برای Windows یا عامل قدیمی Node.js؛ هر چند ثانیه از سرور «کار» می‌گیرد و به دستگاه محلی می‌فرستد | برنامه‌ی Windows برای پرینتر، ترازو و پیجر؛ Node.js برای کارتخوان |
| **۳. صفحه‌ی وب روی خود دستگاه** | آدرس URL در مرورگر دستگاه باز می‌شود | تبلت آشپزخانه، کیوسک |

هر دستگاه یک **کد اتصال** یکتا دارد (از صفحه‌ی همان بخش ساخته می‌شود). API دستگاه‌ها: `/api/device/{code}/{action}` (بدون نیاز به ورود؛ امنیت با رمز بودن کد).

## ۱) پیجر فودکورتی
جریان: سفارش «آماده» می‌شود (یا دکمه‌ی «🔔 زنگ بزن») ← پیجر در پایگاه داده `ringing` می‌شود و **صف زنگ** ایجاد می‌شود ← فرستنده‌ی پیجر فرمان می‌گیرد ← تأیید ارسال ثبت می‌شود.

- **فرستنده‌ی USB/Serial روی صندوق** (ساده‌ترین): در صفحه‌ی «پیجر فودکورت» ‹ «اتصال از همین مرورگر» دکمه‌ی *اتصال به فرستنده* را بزنید، پورت را انتخاب کنید و **قالب فرمان** را مطابق دفترچه‌ی فرستنده وارد کنید (مثلاً `R{n}\r\n` یا `{n:3}\r`). تا وقتی صفحه باز است، هر زنگ مستقیم ارسال می‌شود. نیازمند Chrome/Edge و HTTPS.
- **فرستنده روی شبکه/رایانه‌ی دیگر**: دستگاهی از نوع «فرستنده‌ی پیجر» بسازید و در پل تنظیم کنید:
  `{ "code":"pager01","kind":"pager","transport":"serial","path":"COM3","baud":9600,"format":"R{n}\r\n" }` یا `transport:"tcp"` با `host/port`.
- API خام (برای هر سیستم دیگر): `GET /api/device/{code}/pager` ← `{rings:[{id,number}]}` و `POST` با `{ids:[…]}` برای تأیید.

> قالب فرمان هر برند پیجر (LRS، Retekess، …) متفاوت است؛ نرم‌افزار آن را «قابل تنظیم» گرفته و حدس نمی‌زند.

## ۲) کارتخوان (POS) و پرداخت خودکار در کیوسک
**واقعیت فنی:** «اتصال نرم‌افزار به کارتخوان» در ایران قابلیتی به‌نام **PC‑POS / PcToPos** است که باید توسط **PSP همان دستگاه** (سامان‌کیش، به‌پرداخت ملت، پارسیان، سداد، آسان‌پرداخت، ایران‌کیش، دماوند، فن‌آوا…) روی دستگاه و پایانه‌ی شما **فعال** شود و پروتکل هر PSP اختصاصی است. دستگاه به رایانه‌ی صندوق با **کابل سریال RS232 (یا USB‑Serial)** یا **شبکه (TCP/IP)** وصل می‌شود؛ مستندات رسمی (SDK/DLL/پروتکل) را خود PSP می‌دهد. آنچه در این نرم‌افزار آماده است، «بقیه‌ی مسیر» است:

```
کیوسک (تبلت/مانیتور لمسی)  ──HTTPS──►  سرور  ◄──HTTPS هر ۲ ثانیه──  برنامه‌ی پل (رایانه‌ی صندوق)  ──RS232 / TCP──►  کارتخوان
```
۱. مشتری در کیوسک «کارتخوان» را انتخاب می‌کند؛ سفارش با وضعیت **در انتظار پرداخت** ثبت می‌شود (هنوز به آشپزخانه نمی‌رود) و یک درخواست پرداخت ساخته می‌شود.
۲. برنامه‌ی پل درخواست را می‌گیرد (هر درخواست **فقط یک‌بار** تحویل داده می‌شود تا هرگز دو بار از مشتری پول کم نشود) و **مبلغ را خودکار به دستگاه می‌فرستد**. مشتری فقط کارت می‌زند و رمز می‌زند.
۳. نتیجه (تأیید + شماره پیگیری/RRN، یا خطا) برمی‌گردد؛ با تأیید، سفارش «پرداخت‌شده» می‌شود، به آشپزخانه/پرینتر می‌رسد و سند حسابداری صادر می‌شود. با خطا، کیوسک «تلاش دوباره / پرداخت در صندوق / لغو» را نشان می‌دهد.
۴. اگر برنامه‌ی پل وسط کار قطع شود یا نتیجه نرسد، درخواست پس از ۳ دقیقه ناموفق می‌شود؛ اگر پول واقعاً کم شده بود، صندوقدار در «تبلت و پوز» با «پول کم شده؟ تأیید دستی» (و شماره رسید) سفارش را پرداخت‌شده ثبت می‌کند. سفارش‌های پرداخت‌نشده‌ی رهاشده پس از ۱۵ دقیقه خودکار لغو می‌شوند.

### پروتکل‌ها (در برنامه‌ی پل، فیلد `protocol`)
| پروتکل | برای چه | توضیح |
|---|---|---|
| `saman-ssp1126` | پوزهای **سامان‌کیش** (و PSPهای هم‌خانواده با SSP1126) | ISO‑8583 روی **TCP (پورت پیش‌فرض ۱۱۹۷)** یا **RS232 (۸‑N‑۱، ۱۹۲۰۰ baud)** با SDK متن‌باز `saman-payment-pos` (مهندسی‌معکوس‌شده از کامپوننت رسمی؛ نویسنده آن را روی دستگاه واقعی تست کرده). نصب: `npm i saman-payment-pos` و برای سریال `npm i serialport`. ⚠️ ابتدا PC‑POS را از سامان‌کیش فعال کنید؛ بدون فعال‌سازی دستگاه پاسخ نمی‌دهد. |
| `http` | PSPهایی که سرویس محلی می‌دهند (مثلاً سرویس ویندوزی به‌پرداخت که روی `127.0.0.1` گوش می‌دهد) | آدرس، بدنه با جایگزین `{amountRial}`، و نام فیلدهای نتیجه/پیگیری قابل تنظیم است. |
| `exec` | PSPهایی که فقط برنامه/DLL می‌دهند (می‌توانید یک exe کوچک بنویسید که DLL را صدا بزند) | کد خروج ۰ = تأیید؛ آخرین کلمه‌ی خروجی = شماره پیگیری. |
| `raw` | هر پروتکل ساده‌ی سریال/TCP که مستندش را دارید | فریم درخواست (`\x02…\x03` + LRC اختیاری)، شرط پایان پاسخ و Regex موفقیت/پیگیری. |
| به‌پرداخت ملت | معمولاً «POSPC / پروتکل ۳»: سرویس ویندوز که روی `127.0.0.1` است | با `http` یا `exec` طبق مستند همان سرویس. |

> برای پروتکل‌های **غیر سامان‌کیش** من مستند رسمی/تست‌شده‌ای نداشتم؛ به‌جای حدس‌زدن بایت‌ها، آداپتورهای عمومی (`http` / `exec` / `raw`) را گذاشتم که با مستندی که PSP شما می‌دهد پر می‌شوند. کار آداپتور اختصاصی هر PSP، افزودن یک تابع به `posProtocols` در `agent.mjs` است.

### راه‌اندازی گام‌به‌گام
1. از PSP بخواهید **PC‑POS** را روی پایانه‌ی شما فعال و پارامترهای اتصال (IP/پورت یا Baud) را اعلام کند.
2. در «تبلت و پوز» یک دستگاه از نوع «دستگاه پوز» بسازید (کد اتصال ساخته می‌شود).
3. در همان صفحه، بخش «راه‌اندازی اتصال کارتخوان» را پر کنید؛ فایل `bridge.config.json` ساخته می‌شود.
4. روی رایانه‌ی صندوق (Node.js 18+): `node agent.mjs bridge.config.json` (برای راه‌اندازی خودکار با ویندوز از Task Scheduler / NSSM یا `pm2` استفاده کنید).
5. در «سفارش‌گیر کیوسک» گزینه‌ی «پرداخت با دستگاه کارتخوان» را روشن و دستگاه را انتخاب کنید؛ وقتی پل متصل باشد وضعیت «● متصل» می‌شود و گزینه در کیوسک ظاهر می‌شود.
6. **تست بدون پول:** `node pos-emulator.mjs http 8080` (یا `raw 5000`) یک «کارتخوان آزمایشی» است؛ پل را به آن وصل کنید تا کل مسیر را بدون دستگاه واقعی امتحان کنید.

اگر ابزار فروشنده ندارید: صندوقدار از «سفارش‌ها ‹ جزئیات ‹ 💳 کارتخوان» مبلغ را می‌فرستد یا مبلغ را روی دستگاه می‌زند و با «تأیید دستی دریافت» (شماره رسید) ثبت می‌کند.

## ۳) پرینتر
- **چاپ با مرورگر (ساده و مناسب فارسی)**: `سفارش ‹ رسید` صفحه‌ی ۸۰ میلی‌متری باز می‌کند؛ با فعال‌کردن حالت `--kiosk-printing` در Chrome، بدون پنجره‌ی تأیید چاپ می‌شود.
- **پرینتر ابری/شبکه**: هر سفارش خودکار در صف چاپ (`print_jobs`) می‌رود؛ برنامه‌ی Windows از `/api/device/{code}/jobs` می‌گیرد و با ESC/POS روی TCP، Serial یا صف چاپ USB ویندوزی می‌فرستد. کدگذاری چاپ فارسی قابل تنظیم است و پشتیبانی کدپیج به مدل پرینتر بستگی دارد.

## ۴) تبلت
تبلت آشپزخانه فقط آدرس `/tablet/{code}` را در مرورگر باز می‌کند (نصب برنامه لازم نیست). تبلت/مانیتور لمسی مشتری: `/kiosk/{slug}`.

## برنامه‌ی نصب‌شونده‌ی Windows (پرینتر، ترازو و پیجر)

برای چاپ ابری و اتصال ترازو، نسخه‌ی دسکتاپ Rust را از **GitHub → Actions → Windows hardware bridge → آخرین اجرای موفق → Artifacts** دریافت کنید. فایل Setup را نصب کنید، تنظیمات JSON ساخته‌شده در همین صفحه‌ی پنل را وارد کنید و اتصال را شروع کنید. این برنامه چند دستگاه را هم‌زمان اجرا می‌کند و از اجرای خودکار همراه Windows پشتیبانی می‌کند.

پرینتر شبکه با TCP، پرینتر USB-Serial با COM، و پرینتر USB نصب‌شده در Windows پشتیبانی می‌شود. برای چاپ USB مستقیم، نام صف Windows را در تنظیمات پرینتر وارد کنید و مطمئن شوید درایور آن صف داده‌ی RAW/ESC-POS را می‌پذیرد. ترازو از TCP، COM یا USB HID پشتیبانی می‌شود؛ قالب پاسخ و Regex استخراج وزن باید با مدل ترازو هماهنگ باشد. فرستنده‌ی پیجر هم از TCP و Serial استفاده می‌کند.

کارتخوان در حال حاضر از برنامه‌ی نصب‌شونده‌ی Rust پشتیبانی نمی‌شود؛ برای پروتکل‌های POS از عامل Node.js پایین همین صفحه استفاده کنید. تبلت آشپزخانه در مرورگر دستگاه و آدرس `/tablet/{code}` اجرا می‌شود.

## اجرای پل قدیمی Node.js (کارتخوان)
```
node agent.mjs bridge.config.json      # Node.js 18+؛ برای POS
npm i serialport iconv-lite            # فقط در صورت نیاز به Serial / کدپیج فارسی
```
نمونه‌ی تنظیمات در ابتدای `public/bridge/agent.mjs` آمده و فایل از `/bridge/agent.mjs` روی همین سرور هم قابل دانلود است.
